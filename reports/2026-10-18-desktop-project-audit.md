# 桌宠项目跨模块检查与调整方案

检查日期：2026-10-18。代码基线：`a396f14`，版本号 `1.7.53`；同时包含工作区内尚未发布的旧备份兼容修复。

结论：常规测试和构建通过，但仍有需要修复的数据安全、恢复、交易和在线更新缺陷。建议下一轮先做稳定性修复，再增加功能。这里列出的优先级是修复顺序，不表示每个学生都必然遇到。

本轮按 code-review-excellence 方法将结论分为「隔离复现」「代码链路确认」「尚需环境验证」。没有修改业务代码、学生正式存档、生产接口或发布指针。上一轮备份修复保留原样。本报告与诊断脚本是本轮新增内容。

## 2. 发布前优先修复：6 项 P1

### F01：数据库打开失败会进入删除数据库的恢复流程

- 证据：`src-tauri/src/db/mod.rs:21`、`:28`、`:37`；初始化失败最终在 `src-tauri/src/lib.rs:162` 调用 `expect`。
- 触发：打开数据库、设置 pragma、校验或迁移失败，且错误字符串不是代码识别的两种锁错误。
- 影响：程序先尝试删除 WAL/SHM，再尝试删除主数据库；没有先保存故障副本。I/O、权限等错误并不等价于数据库可丢弃。WAL 也可能含已提交但尚未合并进主文件的数据。localStorage 尚在不代表 SQLite 独有数据一定安全。
- 证据等级：代码链路确认；未对真实数据库执行破坏性复现。
- 调整：停止自动删除；按 SQLite 错误码区分忙碌、只读、满盘、损坏，短暂锁定可有限重试。保留数据库及伴随文件，提供可恢复的故障副本；必要时进入只读恢复界面。初始化失败返回可处理状态，避免直接 panic。
- 验收：临时目录中注入只读、磁盘写错、损坏及锁定场景，原始文件保持可恢复，不能静默创建空账号。
- 原理参考：[SQLite WAL 官方说明](https://sqlite.org/wal.html)。

### F02：本地钱包损坏时，有完好的 SQLite 副本仍可能被识别为需要领养

- 证据：`src/lib/persist.ts:29` 在同一个 try 中解析两份数据，任一解析失败最终直接返回 localStorage 原文；`src/stores/petStore.ts:1173` 捕获加载失败，finally 仍可设置 `loaded=true`。
- 隔离复现 D1：本地钱包设为损坏 JSON、SQLite 保留有效钱包；`dualLoad` 返回损坏内容，`petStore.load()` 返回 false，但 `loaded=true` 且宠物列表为空。
- 影响：真正的老用户数据故障与新用户无存档混在一起，可能重新出现领养提示；后续新操作还可能覆盖旧数据。**这是新确认的触发链，不等于已证实它就是之前所有学生截图的原因。**
- 调整：两份快照独立解析、独立校验，再选择有效版本；记录修复来源。加载状态细分为 loading / ready / empty / recovery-required，只有确认完全没有存档才进入领养。
- 验收：本地坏/SQLite 好、反过来、两份都坏、超时、正常首次启动分别测试；故障态不能保存默认钱包。

### F03：恢复成功后旧内存状态仍能覆盖刚恢复的存档

- 证据：`src/components/settings/SettingsPage.tsx:357` 只调用恢复后展示弹窗；`:408` 允许取消，未重新加载所有 store；`src/lib/backup.ts:410` 更新持久化数据但没有同步内存。饥饿定时器、桌宠同步请求也会调用 `petStore.save()`。
- 隔离复现 D2：当前内存 1000 金币，恢复备份后磁盘为 4321；调用现有 `save()` 后又变回 1000。
- 调整：加入全应用恢复屏障，暂停主窗和桌宠写入；恢复提交后统一重新加载所有状态并同步桌宠，或在屏障保持期间自动重载主界面。不能让「取消重启」回到旧数据可写状态。
- 验收：恢复过程中触发签到、饥饿计时、桌宠同步；恢复后不点重启、关弹窗、刷新，都不能写回恢复前的状态。

### F04：典藏卡、衣橱及部分购买仍可能扣款成功但物品未保存

- 证据：`src/stores/collectorCardStore.ts:44` 先 `spendCoins` 后保存卡片；`src/stores/profileStore.ts:94` 购买和 `:119` 改名同样分两次保存；`src/components/pet/WorkshopShop.tsx:130` 扣款后再加入蛋。`dualSave` 没有向调用方报告持久化失败。
- 隔离复现 D5：模拟卡片存储及其 SQLite 写入失败，购买仍返回成功，钱包从 1000 降到 112，重新加载后卡片不存在。衣橱和工坊是同类代码风险，本次没有逐个注入相同故障。
- 调整：复用已有安全交易机制，把钱包、物品、兑换/购买记录一起提交；成功持久化后再更新界面。将卡片、衣橱、改名、工坊蛋列入迁移清单，逐项收口；不重写已有正常的配饰/品质交易。
- 验收：交易每个写入点失败和中断重启，只允许「扣款且到账」或「两者均未发生」；连点、跨窗口只能购买一次。

### F05：补偿码核销后丢响应，重试会永久显示已兑换

- 证据：`cf-workers/api.js:1275` 无条件拒绝 used 状态；`:1285` 先占用码；`:1289` 再更新状态。客户端 `src/components/courses/RedeemCode.tsx:35` 收到响应后才增加金币/经验和本地记录。
- 隔离复现 D9：模拟服务器第一次成功返回、客户端未消费响应；同一设备重试得到 400「此补偿码已被兑换」。此外两个数据库语句之间失败也存在占位已成功、状态未同步的窗口。
- 调整：保留 **优秀码本地、补偿码联网** 的产品选择。补偿码为首次领取产生稳定回执 ID；同一已认证领取身份重试返回同一回执，不再发第二笔奖励；其他身份仍拒绝。服务器占用与回执使用事务，客户端把奖励和已应用回执一起原子保存。
- 兼容要求：为旧客户端保留原接口语义或使用新版本接口，不能给没有本地原子去重的旧版本直接增加重放成功能力。
- 验收：断网丢响应、响应到达前退出、本地写失败、相同回执重放；最后恰好到账一次。

### F06：题库在线更新整包缓存过大，可能一直退回旧内置题库

- 证据：`src/question-bank/repository.ts:252` 下载 manifest 的所有文件，`:262` 将全部内容序列化到一个 localStorage key；`src/App.tsx:322` 吞掉更新异常。
- 实测当前发布文件组序列化后为 5,045,257 个 JS 字符，UTF-8 5,746,259 字节；按 UTF-16 计约 **9.62 MiB**。这还未计算用户已有存档。
- 隔离复现 D7：模拟旧版内置 manifest，使更新分支执行，在 5 MiB 存储配额下抛出 QuotaExceededError，current 缓存未写入。此为配额模型复现，本次未测量老师那台 WebView2 的实际配额。
- 影响：新安装包与线上 manifest 完全相同时会跳过整包缓存，所以不一定立刻报错；后续只在线更新题库时，老客户端可能下载成功但保存失败，再次启动又下载并继续用旧版。
- 调整：桌面版按内容哈希保存到 AppData 文件缓存；浏览器预览用 IndexedDB。仅在 localStorage 存小 manifest/当前版本指针；按渠道下载、校验完毕后切换版本，并保留上一份有效快照。失败显示非阻断的更新状态，内置练习继续可用。
- 验收：超过 10 MiB 的题库、断网、容量不足、部分文件损坏、在线版本回退；不能占满金币存储，也不能反复全量下载。

## 4. 潜在风险与优化项

这些项与上面的可复现缺陷分开，不宣称已发生数据泄漏或已被攻击。

### R01：教师认证需要加固（建议 P1，服务端可先行）

`cf-workers/api.js:439` 使用单次 SHA-256 加固定字符串；教师登录 `:1093` 没有该端点的应用层失败次数限制，token 只有轮换、未见过期校验。单次快速哈希不适合作为长期密码存储。

建议增加经批准的自适应密码派生算法、每用户随机盐及参数版本；旧账号成功登录时平滑升级，避免统一要求重设。登录按账号和网络来源限速；短期令牌和撤销机制逐步迁移。先确认 Cloudflare 现有外部防护规则及运行时计算预算，本次未检查控制台配置。测试不能对真实教师账号进行暴力尝试。

### R02：依赖公告、内容安全策略和权限边界（建议 P2）

官方 npm 审计命中 DOMPurify 3.4.11、pdfjs-dist 6.1.200、react-router / react-router-dom 7.18.0。镜像 registry 的 audit 接口不支持，已改用官方 registry 验证，未执行自动升级。

- React Router 公告针对不稳定 RSC 接口；本项目桌面使用 BrowserRouter / MemoryRouter，未发现该调用路径。建议升级兼容的修复小版本，但不把它记为已确认的桌面 CSRF 漏洞。[维护方公告](https://github.com/remix-run/react-router/security/advisories/GHSA-qwww-vcr4-c8h2)
- pdfjs-dist 目前仅找到题库离线提取脚本使用，未在桌面 src 发现 PDF 查看器。需更新至公告修复版本或更新的兼容版本，并把仅用于构建的依赖移到 devDependencies；不宣称学生打开主界面就会触发该漏洞。[维护方公告](https://github.com/mozilla/pdf.js/security/advisories/GHSA-hq66-cqwq-w95j)
- DOMPurify 当前调用为 sanitize 字符串，未发现 IN_PLACE、CUSTOM_ELEMENT_HANDLING 等审计公告对应配置；仍应升级并保留代码/图片渲染回归。[维护方公告示例](https://github.com/cure53/DOMPurify/security/advisories/GHSA-6688-9rhm-gjv2)
- `src-tauri/tauri.conf.json` 的 CSP 为 null，两个窗口共用 capability。建议先建立资源来源清单及 CSP 兼容测试，再收窄脚本/连接来源和窗口权限；目前没有发现可据此直接确认的注入利用链，不能贸然禁用 blob 图片或远程教学资源。

### R03：网络故障可能被误报为空数据，缓存仍需治理（建议 P2）

`WorkshopShop.tsx:85` 的静态目录请求没有总超时，动态请求 catch 后显示「还没有老师上传精灵」；`src-dungeon/utils/api.ts:64` 请求没有统一超时，直接解析 JSON。`spriteDownloader.ts` 只检查旧缓存文件存在，失败修复可能反复使用同一损坏文件。

建议统一处理 HTTP 状态、非 JSON 响应、超时、取消和重试；读取失败、真正空目录、离线缓存必须是不同状态。素材用哈希/版本校验、临时文件完成后切换，下载失败保留前一份有效素材。内容缓存允许清理，存档不能与缓存一起删除。

### R04：离线同步、免费资源容量及迁移风险（建议 P2）

`src-dungeon/stores/dungeonStore.ts:499` 战斗上报及备用同步都是临时异步任务，断网后没有持久化待同步队列；两次都失败时本地有进度，服务器未必有。`cf-workers/api.js:378` 限流的读、判断、写分离，高并发存在竞争；每次尝试还消耗 D1 写入。schema 迁移逐条吞掉异常，再标记版本，失败时可能留下部分迁移状态。

建议使用少量、按进度合并的本地 outbox，带稳定事件 ID、退避和服务端去重；不能逐次移动/逐秒同步。schema 用明确版本迁移，仅全部成功才推进版本。限流原子化，并评估边缘限流能力，避免把抗刷请求全部落到 D1。保留静态目录/图片 CDN 方案。

本次没有真实请求量和 Cloudflare 配额使用数据，**不能给出可靠的可承载学生人数**。先测每活跃学生的请求、D1 读写、素材流量及缓存命中，再按「最先触顶的指标」估算，保留余量；不要仅凭安装人数估算。

### R05：启动性能与发布覆盖（建议 P2/P3）

主构建仍有约 1.58 MB 的 App JS 块（gzip 约 459 KB），迷宫独立入口约 1.84 MB（gzip 约 543 KB）。App 静态引入迷宫和多个重页面，可逐步路由懒加载并按需加载 Phaser；是否改善启动时间需低配 Windows 测量，不能只看包体宣称提速。桌宠当前 50 ms 命中采样有清理和重入保护，但应测量 1/2/3 只伙伴及高 DPI 下的 CPU/GPU/内存。

发布流程已有三平台构建、签名及下载校验，应保留；还需补充 Rust 故障测试、Windows WebView2 冒烟、旧存档迁移和跨窗口恢复测试。此前用户免做 Windows 实机不改变本次验证的边界：没有做就不能写已验收。流水线增加只读依赖审计；不要直接运行无评估的 `npm audit fix --force`。

## 6. 可实施的分批方案

| 批次 | 工作包 | 交付/验收标准 | 发布方式 |
| --- | --- | --- | --- |
| A：先保数据 | F01、F02、F03、F07、F08，合入现有备份修复 | 有效副本能恢复；故障不删库、不创建默认钱包；恢复期间全部写操作受控；恢复策略明确且可撤回 | 桌面修复版 |
| B：保证奖励和在线内容 | F04、F05、F06、F09 | 所有购买原子提交；补偿码丢响应也能恰好到账一次；大题库更新不占存档配额且可回退 | 兼容服务端先发布，再桌面版；可与 A 合并但分步验证 |
| C：交互与安全收尾 | F10、F11、F12、R01–R05 | 跨迷宫计时正常、多宠不串动画、资料不丢手机号；完成依赖升级和最低平台冒烟 | F12 后端兼容补丁可先行，其余随桌面稳定版或后续优化 |

第一轮不建议同时改金币数值、品质概率和新玩法，降低回归面。优先形成共享持久化/交易/网络规范：当前反复出现问题的重要原因，是同一类操作分别实现，部分函数失败时只写日志，UI 和测试仍把它当成功。

长线存储方案：逐步将用户数据提交收敛到原生 SQLite 事务和单调 revision，localStorage 保留必要的轻量缓存与启动索引。不要一次性迁移全部存档；先用版本化适配层封装现有 dualLoad/dualSave，并提供迁移前快照、可回滚验证。短期先补当前交易与恢复保护，避免架构重构拖延故障修复。
